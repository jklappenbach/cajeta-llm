[explore: PREPARED-WEIGHT CACHE (working name; NOT a format — see naming note) — a derived, device-keyed sidecar holding the de-interleaved, tile-ordered form of a GGUF's tensors that we already recompute on every load. Keyed by source content hash + tile geometry + quant format; written once, mmapped thereafter; ALWAYS safe to delete because it is reconstructible from the GGUF. Motivation measured 2026-09-13: k-quant blocks interleave scales with quants, so every kernel reads a 16-byte header inside the weight stream and bit-unpacks 6-bit scale fields before arithmetic — llama stages a de-interleaved LDS tile and we build an int8 widen copy, i.e. BOTH engines pay to undo the file layout. Widen kernels cost ~190ms of device time per 8B load, and the whole prefillWeights=auto policy exists to decide per format whether that transform is worth it. Carry a hash of the SOURCE in the sidecar, which GGUF itself has no field for — ties into the security item on the cajeta stack. Do NOT let it become a distributable format: its value is that nobody has to adopt anything. SPEC FINDINGS 2026-09-13: (a) the GGUF spec has NO notion of a derived or cached form -- it describes one self-contained file of metadata + tensor data, so a tile cache sits OUTSIDE it and must never be mistaken for a variant of it; (b) but the container is extensible by convention, a dotted key namespace with a 315-entry registry in llama.cpp gguf-py/gguf/constants.py, so the sidecar can BE a GGUF carrying our own namespaced keys (tile geometry, wave width, source hash) -- no new container, and the cajeta GGUF WRITER now in flight is exactly what makes that possible; (c) CORRECTION to my earlier "GGUF has no integrity story": llama.cpp ships llama-gguf-hash, per-model AND per-tensor, xxh64/sha1/sha256/uuid with manifest --check. The hash is external to the file rather than absent, so the sidecar should record the SOURCE hash in that form rather than inventing one]
